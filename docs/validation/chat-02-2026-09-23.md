# CHAT-02: durable task-linked conversation threads

- Date: 2026-09-23
- Scope: Deck persistence and operator HTTP API for conversation identity
- Environment: local macOS host, isolated temporary SQLite stores and loopback
  Deck processes; no Kind/GCP deployment or live model invocation

## Delivered behavior

Migration `013_conversation_threads.sql` adds threads and task-origin links while
reusing canonical channel messages. Replies carry an optional `thread_id`, and
existing channel history continues to include all messages in append order.

A thread has one root message and may originate multiple tasks. Each linked task
has one immutable originating thread; additional task mentions remain ordinary
canonical references. The same root, or any existing reply, resolves to the same
thread. Repeating an existing task link succeeds without duplicate events;
reassigning its origin conflicts. Promotion creates or reuses the thread and
links the new task atomically. A thread link changes no execution authority,
budget, task status, or selected context.

Operator endpoints create/list/read threads, page replies, link an existing task,
and recover its origin. They use existing operator session and CSRF protection.
Cross-channel replies and cross-project task links are rejected. Linked drafts
must be archived instead of deleted. Archive preserves the origin and history.

Existing promoted messages receive threads during migration. Legacy exports
remain importable, and new exports retain thread IDs, roots, task links, reply
IDs, ordering, and cursors. Import rejects broken thread associations atomically.
Thread creation, task links, and message append publish durable change events;
promotion includes its thread ID in the existing promotion event.

The API and canonical fixtures are in [OpenAPI](../../deck/api/openapi.yaml),
[thread.json](../../deck/api/fixtures/v1/thread.json), and
[channel-message.json](../../deck/api/fixtures/v1/channel-message.json).
No agent-dispatch capability is advertised.

## Deterministic checks

[Store tests](../../deck/internal/store/threads_test.go) cover:

- thread creation replay, task promotion replay, and stable identity after reopen;
- root/reply pagination and rejecting another thread's cursor;
- concurrent creation/link requests producing one thread and one linking event;
- concurrent replies without SQLite lock-upgrade failures or lost messages;
- cross-channel and cross-project rejection and origin reassignment conflicts;
- linked-draft retention, archive, deterministic export/import, and cursor reuse;
- upgrade from the pre-thread schema, preserving unrelated channel messages;
- legacy import and rollback of malformed thread/root/task associations.

[HTTP tests](../../deck/internal/httpapi/threads_test.go) use two independent
operator login sessions to create, recover, link, and reply to the same thread.
The existing authentication route matrix includes every new endpoint, and a
missing CSRF token is rejected on task linkage. Fixture tests decode both new
canonical fixtures.

Commands executed:

```sh
cd deck
go test ./internal/store -run TestThread -count=1
go test -race ./internal/store -run TestThread -count=1
go test ./internal/httpapi -run 'TestProtocol|TestThread' -count=1
```

Root `make check` also passed (installation checks, CLI, Deck backend/frontend,
and Marina tests/vet), as did OpenAPI YAML parsing and canonical fixture checks.

These checks passed. The initially failing concurrency regression reproduced
SQLite `SQLITE_BUSY` during reply append; validating immutable thread ownership
before the write transaction removed the read-to-write lock upgrade.

## Real-process acceptance

[The repeatable acceptance script](../../deck/scripts/test-threads.py) builds Deck
and uses temporary databases, generated test-only authentication, and two
independent cookie jars. It passed:

1. Create a root and recover its thread from a second session without duplication.
2. Append a reply from that session and promote it into a bounded draft task.
3. Recover the same originating thread from the task in either session.
4. Stop and restart the actual Deck process; reuse both sessions and the previous
   reply cursor without replacing thread/message/task identities.
5. Archive the task and retain its thread association.
6. Export the project, import it into a second fresh Deck process, and compare
   the thread, full history, and exported project for equality.
7. Stop both test processes and remove their temporary stores and credentials.

Run from the repository root:

```sh
make -C deck conformance
make conformance
```

Root conformance now includes this Deck acceptance test before the existing CLI
and Marina real-process suites. All three passed, including repository message
promotion and existing context selection, failure, and recovery scenarios.

## Limits

This completes CHAT-02's persistence/API scope. It does not establish agent
selection or LLM invocation, clarification routing, automatic result publication,
or CHAT-10's browser workflow acceptance. Existing message append semantics are
unchanged: thread creation and task linking are replayable, but arbitrary message
append retries do not gain idempotency in this increment. Creating or linking a
thread never dispatches work.

The test proves separate HTTP sessions and real process persistence on the local
host, not two physical devices, a browser UI, or Kubernetes installation behavior.
The running local Kind installation was not deployed by this task.
