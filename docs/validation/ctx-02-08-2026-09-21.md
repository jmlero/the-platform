## Boundaries and upgrade notes

- Sources are explicit: up to 32 project sources, 20 selected messages, 16 KiB per
  authored/Git file input, and 128 KiB per assembled package. Git reads require an
  exact commit and a regular UTF-8 file; symlinks and mutable revisions are rejected.
- Freshness uses explicit expiry. Conflict handling uses declared conflicting
  source IDs. Known override patterns are a conservative filter, not a general
  semantic contradiction or prompt-injection detector. Existing authority,
  budgets, worker isolation and publication gates remain the security boundary.
- Routine edits affect newly authorized work. Revocation is checked at workflow
  and gateway boundaries; an in-flight request is cancelled on the existing live
  authority polling cycle, and a blocker waits for observed worker termination.
- Repository changes stay within the installation's configured GitHub API/clone
  origin and credential reference. Endpoints, credentials, trusted checks,
  runtime and policy changes remain private installation setup. A changed
  installation profile cannot silently alter an old run.
- Existing installations must grant the project-scoped Marina service identity
  `context.read`, `repository.read`, and `repository.write` before enabling the
  updated worker workflow. The installation generator includes these grants.
- Project exports preserve knowledge history and task/run selections; they do
  not recreate Marina's connection or pending association intent on another
  installation. Imported binding snapshots must match Marina's local history
  before execution.
- No new concurrency, automatic replan, semantic review, merge or deploy
  capability is introduced. These changes have not been deployed
  to the existing local Kubernetes or GCP installation.
