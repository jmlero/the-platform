# LAND-02, LAND-03, VER-01 and TEST-01 validation

Date: 2026-10-03. Development source and local packaging validation. This report
does not establish acceptance of the updated installed repository workflow.

## Implementation

TEST-01 adds Playwright 1.63.0, three browser scenarios against Deck's embedded
production frontend, `make -C deck browser-test`, and a GitHub Actions step that
installs Chromium during setup and runs the suite. CI retains failure traces,
screenshots and its HTML report. Unit and browser discovery remain separate.

The landing scenario exposed an operator-view bug: an evidenced landed task still
appeared under Needs attention. The view now uses the same task-stage calculation
as the middle column, so a current landing finishes automatically while stale or
syncing evidence still needs attention. The landed result retains its commit
link and evidence and offers no operator acceptance control. Legacy results keep
their acceptance flow.

LAND-02 adds an exact landing observation and selected evidence to the completed
task through the existing guarded, idempotent completion route. Completion
requires independently passing review, test and landing/CI evidence on that
commit, the authorized repository/base, and the run's unchanged acceptance
criteria. It creates no human acceptance record. Selected prerequisite evidence
must remain current and unexpired; Marina also observes each landed prerequisite
on the exact base chosen for implementation or rebase. A criteria edit before
automatic completion produces a focused blocker requiring a new task.

Export/import retains the completed landing and validates its frozen criteria,
active plan, source, policy and evidence at original completion. Evidence that
expired afterwards remains readable historical data and grants no current
prerequisite authority.

LAND-03 retains the original task/context/budget while admitting a native Git
rebase onto an observed new base. It publishes through a fresh task branch,
independent exact-patch review, clean verification and exact-head CI; existing
refs are never force-pushed. A conflict aborts the rebase and returns a bounded
blocker with retained evidence. Repeated base movement consumes the original
runtime budget. A lost successful landing response followed by another main
commit is recovered through exact-commit ancestry, without repeating the work;
required CI must still pass on that commit.

VER-01 gives the independent verifier and native Codex the same project-specific
toolchain stage in `marina/Dockerfile.verifier`. Its base Node.js and Go images
are pinned by OCI digest. The image freezes the current three-module Go cache,
Deck's locked npm cache, and Playwright's matching Chromium binaries and OS
libraries during build. Runtime Go/npm downloads and automatic browser downloads
are disabled. The verifier explicitly supplies those settings to each clean
check environment. The native target retains the locked upstream static adapter,
Codex CLI, code-mode host and bundled resources/helpers with its original
entry point, unprivileged UID/GID and workspace layout.

real Go Deck process on an allocated loopback HTTP port for each test worker.

The final three Chrome scenarios exercised:

1. Creating and opening a project; explicitly invoking a configured conversation
   fixture; receiving its reply through the real API and SSE path; reloading the
   durable thread and retaining the selected project.
2. Moving a task from To do to In progress to Recently landed; inspecting its

3. Creating a legacy repository task through the browser with explicit repository

responses and execution/review/test/landing evidence are deterministic service
fixtures, including a synthetic commit. These tests do not establish live model
execution, real Git landing, Kubernetes acceptance, authenticated browser
mutations or artifact-byte downloads. The fixture disables demo execution and
isolates its database; teardown stops Deck and removes its temporary data.

## LAND-02 and LAND-03 proof

Environment: macOS development host, temporary Deck/Marina SQLite databases,
deterministic runtime and Git-boundary fixtures. These checks exercise product
state and evidence gates without changing GitHub.

| Owning directory and command | Observed result |
| --- | --- |
| `deck/`: `go test ./internal/store ./internal/httpapi -count=1` | Store and HTTP API suites passed. |
| `marina/`: `go test ./internal/flow ./internal/workresult ./internal/worker ./internal/sourcecontrol/... -count=1` | All five packages passed uncached. |
| `marina/`: `go test ./internal/flow -run TestChangedAcceptanceCriteriaBlocksAutomaticCompletionWithClearReason -count=1` | Final criteria-edit regression passed through a complete valid flow to the completion boundary, then a clear terminal blocker. |
| `marina/`: `go test ./internal/flow -run 'TestRebaseReobserves|TestMainMovementBetween' -count=1` | New-base prerequisite and observation/fast-forward race regressions passed. |

The Deck regression first reproduced old-scope evidence completing an edited
task. Five tampered-import scenarios also first imported successfully: changed
criteria, another selected plan, another policy, another source and evidence
expired before landing. The fixes reject these cases atomically. The historical
case with evidence expiring after original completion still imports. HTTP
coverage checks exact replay after reopening the database, rejects changed
landing replay, releases and claims a dependent task without human acceptance,
and preserves landing through export/import.

The deterministic rebase flow reopens SQLite between every state transition and
loses engine-start, commit and evidence responses. It finishes with six runtime
starts, two commits and one landing; completion selects only final-head passing
evidence. Other regressions show:

- A conflicting native rebase records its conflicting path, retains the pinned
  task history and result artifact, and publishes no commit or passing evidence.
- Repeated main movement stops at six original runtime starts, with two commits
  and no landing; the budget and deadline do not expand.
- A rebase after repair finishes in ten starts and three commits while retaining
  the earlier failure, exact source revision and saved diagnosis unchanged.
- A prerequisite missing from a rewritten base blocks before runtime admission.
  An available prerequisite admits rebase on that exact new base.
- Main movement between observation and guarded fast-forward retains the
  unresolved state; the next reconciliation schedules a rebase with fresh gates.
- A verified task commit already contained in advanced main spends no rebase
  starts and writes no refs. Failed CI at that exact commit still enters repair.
- Implementation and rebase instructions require the frozen configured checks
  with the prepackaged toolchain and prohibit runtime dependency/browser
  downloads. This instruction regression failed before the prompt change.

These fixtures establish durable workflow behavior, not installed native model,
GitHub or Kubernetes acceptance. Native Git rebase/conflict proof is deferred at
the operator's explicit choice to keep GitHub unchanged. Application images may
be built and imported locally; deployment and private installation changes are
outside this validation step. Root product/conformance results and local image
evidence follow below.
